# 项目演示与求职材料

## 三分钟演示顺序

1. 启动真实模型服务，打开本机 8001 页面（Docker 使用 8002）。展示知识库文档列表和模型模式。
2. 上传 samples 中的文档，提出“默认端口是什么，怎么修改？”。展示流式回答、Markdown 与原文引用；打开引用核对答案。
3. 切换版本过滤，说明不同版本的知识如何隔离；用检索模式切换展示向量、BM25、混合与重排。
4. 问一个资料中没有的问题，展示拒答。说明拒答和引用校验都有局限，引用编号正确不等于每句话都受证据支持。
5. 展示 eval/REPORT.md：四方案的证据命中率和延迟。dev/test 均已匹配新版标签；测试集首位证据命中率由向量 50% 到重排 65.625%，中位延迟约从 941 ms 到 2134 ms，体现效果与延迟的代价。
6. 展示 Docker 验收记录和 25 项 Python 回归结果，说明重启持久化、错误提示及流式中断处理。

录屏前隐藏终端中的密钥、账户信息和私人文档。建议录制 2–3 分钟，留下问题输入、引用展开和检索模式切换的真实操作。当前未生成录屏，不把脚本说明当成演示视频。

## 简历项目描述草稿

项目名称：知源——可追溯 RAG 知识库问答系统

技术栈：Python、FastAPI、兼容 OpenAI 格式的 LLM API、Qdrant、BM25、RRF、BGE Reranker、Docker Compose。

- 构建文档入库、版本过滤、检索、流式问答与删除的完整流程，使用 Qdrant 存储向量、SQLite 管理文档元数据与追踪记录。
- 实现向量与 BM25 混合检索、RRF 融合及可选重排，支持来源引用、资料不足拒答和生成后文档状态复查。
- 补充模型超时、有限退避重试、脱敏错误提示及流式中断检测；配置 Docker 健康检查、数据库就绪等待和独立持久化验收。
- 基于 16 篇固定版本文档构建 80 题评测集，对比四种检索方案，记录证据命中与延迟；建立 Python 回归和前端 Markdown 安全检查。

使用前按自己实际参与和掌握程度调整措辞。代码经 AI 辅助实现，不应声称独立手写全部代码。当前不写“生产级”“准确率提升至 81.25%”；缺少对应证据。GitHub CI 已运行通过，可展示仓库 Actions 记录。新版测试集已重测，量化指标须连同题量、锚点匹配定义及单轮测量条件一起解释，不将其当作答案准确率。

## 面试需要讲清的设计

- 为什么使用混合检索：向量负责语义相近，BM25 补充术语和标识符；RRF 融合排名，避免直接相加不同量纲的分数。
- 为什么重排可选：增加一次模型调用和延迟，需要用同一评测集比较收益，而不是默认认为更复杂就更好。
- 引用有什么边界：校验编号和文档状态可减少无效引用，不能证明所有自然语言结论都被原文支持。
- 如何处理模型失败：只对限定连接错误和状态码重试；生成中途失败明确提示，不自动重新播放整段请求。
- 当前瓶颈：BM25 查询时重建、同步模型调用、单进程、小语料；尚无多租户权限、任务队列和并发压测结果。
- 下一步如何改进：人工复核标签并冻结新测试集，评估章节切分，再按瓶颈引入后台导入和缓存。
